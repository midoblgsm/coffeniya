# ☕ Coffeniya

Supplier and inventory management for independent coffee shops.

Shop owners sign in, set up their shop, track suppliers and stock levels, get
low-stock alerts, and manage purchase orders end to end — placing orders with a
supplier and receiving them back into stock.

## Stack

| Layer     | Technology                                                      |
| --------- | --------------------------------------------------------------- |
| Frontend  | [Vite](https://vitejs.dev) + React + TypeScript (`web/`)        |
| Backend   | Firebase Cloud Functions, TypeScript (`functions/`)             |
| Database  | Cloud Firestore (`firestore.rules`, `firestore.indexes.json`)   |
| Files     | Firebase Storage (`storage.rules`)                              |
| Auth      | Firebase Authentication (email/password + Google)               |
| Hosting   | Firebase Hosting (SPA rewrite to `web/dist`)                    |
| CI/CD     | GitHub Actions (`.github/workflows/`)                           |

## Architecture notes

- Each user belongs to one **shop** (`shops/{shopId}`); suppliers, inventory
  items, and purchase orders are subcollections scoped by Firestore rules to
  shop members.
- Shops are created only via the `createShop` callable function, keeping
  `users/{uid}.shopId` and shop membership consistent.
- Receiving a purchase order goes through the `receiveOrder` callable, which
  transactionally marks the order received and increments stock — clients are
  blocked by rules from setting an order to `received` themselves.
- Supplier documents (contracts, price lists) upload to Storage under
  `shops/{shopId}/…`; Storage rules check shop membership via a
  cross-service Firestore lookup.

## Local development

```bash
# Install dependencies
npm ci                    # root: firebase-tools (emulators/deploys)
npm ci --prefix web
npm ci --prefix functions

# Start the Firebase emulator suite (auth, firestore, functions, storage)
npm run emulators

# In another terminal: run the app against the emulators
cd web
VITE_USE_EMULATORS=true VITE_FIREBASE_PROJECT_ID=demo-coffeniya \
VITE_FIREBASE_API_KEY=demo-api-key npm run dev
```

The Firestore/Storage emulators need a JVM (Java 11+).

## Tests

```bash
npm test --prefix web        # frontend unit tests (Vitest)
npm test --prefix functions  # functions unit tests (Vitest)
npm run e2e                  # Playwright e2e against the emulator suite
```

`npm run e2e` builds the functions, boots the emulators with the demo project
`demo-coffeniya`, starts the Vite dev server, and drives a full user journey:
sign-up → create shop → add supplier → add low-stock item → place a purchase
order → receive it → stock replenished.

## CI/CD

### Repository configuration

Secrets (Settings → Secrets and variables → Actions → Secrets):

| Secret                     | Value                                                          |
| -------------------------- | -------------------------------------------------------------- |
| `FIREBASE_SERVICE_ACCOUNT` | JSON key of a service account with deploy permissions¹         |

Variables (Settings → Secrets and variables → Actions → Variables):

| Variable                            | Value                                     |
| ----------------------------------- | ----------------------------------------- |
| `VITE_FIREBASE_API_KEY`             | Web app API key                           |
| `VITE_FIREBASE_AUTH_DOMAIN`         | `<project>.firebaseapp.com`               |
| `VITE_FIREBASE_PROJECT_ID`          | Project ID (also used as `--project`)     |
| `VITE_FIREBASE_STORAGE_BUCKET`      | Storage bucket                            |
| `VITE_FIREBASE_MESSAGING_SENDER_ID` | Sender ID                                 |
| `VITE_FIREBASE_APP_ID`              | Web app ID                                |

¹ e.g. the key generated by `firebase init hosting:github`, or a service
account with the *Firebase Admin* role (needed to deploy functions, rules and
indexes in addition to hosting).

### Workflows

- **`pr.yml`** — on every pull request:
  - unit tests + type-checked builds (web and functions)
  - Playwright e2e tests against the Firebase emulator suite
  - `npm audit` vulnerability scan (fails on high severity in production deps)
  - a Firebase Hosting **preview channel** deploy (`pr-<number>`, expires in
    7 days, link posted on the PR; skipped for forked PRs, which can't read
    secrets)
- **`deploy.yml`** — on every push to `main` (i.e. PR merge): runs unit tests,
  builds the app, and deploys **hosting, functions, Firestore rules + indexes,
  and Storage rules** to production with
  `firebase deploy --only hosting,functions,firestore,storage`.
